# Transfer posting contract

Migration 0008 is additive and needs no backfill. `transfer_details` holds the actual positive source debit and destination credit; equal currencies require equal amounts. Both accounts and the parent/optional fee transaction are household-scoped foreign keys. The fee is a child transaction (`type='fee'`, `parent_transaction_id` = transfer ID), with its money in `posting_details`. The fee comes from the source account/currency. Its category is an active expense category. For a foreign-currency fee, use the existing manual decimal exchange-rate calculation and store the exact resulting RSD minor units; do not derive principal amounts by conversion. `transaction_reporting_movements` contains posted expense, income, fee and refund transaction movements, excluding transfer principal, opening balances and adjustments. Its amounts are signed.

## Atomic batch protocol

Use the existing posting repository and one D1 `batch`, never Prisma `$transaction` or a read/check followed by a separate write. Bind user data as parameters. Validate normalized input before SQL: actual amounts and fee are decimal-string positive safe integers, supported currencies, real date and valid rate/source pairing. Use integer arithmetic and decimal strings for bindings; never float-convert money. On create use the existing `posting_requests`, `posting_request_checks`, `idempotency_keys`, and `posting_replay_checks` protocol with the **same household/member/key scope and canonical payload across all posting kinds**. A different payload, including a different kind, conflicts. Replay returns the original `response_json`, even after edits or voids. Membership must still be current on replay.

Before writes, insert into `transfer_checks(household_id,member_id,transaction_id,version,operation,expected_json)` using `operation` `post`, `edit`, or `void`; `expected_json` is the normalized TransferInput on post/edit and may be `{}` on void. The trigger checks active membership, current parent version and status, eligibility of old and new accounts and fee category, and projected balances after removing *all* old parent and currently posted fee movements and applying new legs and fee. It subtracts reserves and rejects negative available funds and balances above the safe integer limit. SQLite integer SUM overflow also aborts. Do not rely on a preflight read for these checks. Use the transaction's expected version in the guarded UPDATE, increment it exactly once, and insert `posting_write_checks(changed)` with `changes()` immediately after every required single-row UPDATE/DELETE/INSERT, including claim, details, parent, fee, movements, audit, key and snapshot writes. This makes ignored/zero-row writes abort inside the batch.

Create two principal `account_movements` of type `transaction`, one negative debit and one positive credit, using the actual currencies and transaction date. Existing account currency lock trigger then locks both. Create at most one fee child, its `posting_details`, and one negative movement. On edit delete old principal/fee movements, update details/parent, and recreate effective movements. Reuse the current fee child when still present; when removing a fee, void its child (retain its details/history) and clear `fee_transaction_id`; when adding later create a fresh child. On void remove the principal/fee movements and void parent and current fee child. Do not permit direct fee edit or void. Old accounts must be active even if they are no longer selected; a spent destination credit or reserved money may prevent edit/void. Audit contains before/after snapshots; do not delete financial history.

As the last assertion before the batch snapshot SELECT, insert into `transfer_result_checks(household_id,transaction_id,version,operation,expected_json,fee_id,fee_rsd,audit_id,claim_id)`. `version` is the resulting parent version, `fee_id` the current fee ID or null, `fee_rsd` the positive exact fee RSD amount or null, `audit_id` the inserted audit, and `claim_id` the request claim ID for post (null otherwise). It asserts parent/details, precisely two correctly signed principal movements, the linked fee and its single movement, absence of other posted fee children, audit, and the idempotency result on post. For void it asserts zero parent movements and no posted fee children. Follow with the response snapshot SELECT in the same batch; the post snapshot stored in `posting_requests.response_json` must be the original response. Audit and result checks are not a substitute for immediate `posting_write_checks`.

Ordinary list/detail reads should use Prisma with `household: { status: 'active', members: { some: { identitySubject, status: 'active' } } }` in the same scoped `where`, and include `postingDetails`, `transferDetails` and fee/children as needed. The write batch and its snapshot SELECT are the D1 exception. Preserve stable cursor ordering and bound result sizes. Foreign key constraints and triggers remain SQL-authoritative; Prisma models map them, not migrations.

## Recovery

There is no destructive migration or existing-row rewrite. Before deploying, back up and test the migration and application together. Reverting application code alone leaves the additive schema in place; after transfers exist, do not drop its table or discard fee/ledger history. Restore from a verified D1 backup or use a forward repair migration if recovery is required.
