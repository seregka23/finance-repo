# Refund storage and atomic write contract

Migration 0009 adds `refund_details`: one row per refund, a scoped purchase FK and a unique, positive, permanent allocation sequence per purchase. The transaction's `parent_transaction_id` must match the detail at insertion; the detail is immutable. Do not reuse sequences from voided refunds. `posting_details` stores each refund's credited account, positive amount and original conversion snapshot. Prisma's `refundDetails`, `purchaseRefunds`, `parent` and `postingDetails` support ordinary scoped eager reads. SQL migrations, not Prisma, govern constraints. Legacy data is unchanged.

A refund inherits its posted expense purchase's category, currency, rate and source; clients cannot override them. Archived historical expense categories can be inherited. The destination must be an active account in the purchase currency, even if the purchase account is archived. A missing or inconsistent conversion snapshot produces a 409: do not invent a rate. RSD purchases with null rate are valid when the stored RSD equals the amount. A zero RSD allocation is valid. `cumulativeRefundRsd` uses exact BigInt conversion and half-up rounding, not a floating-point SQL expression or proportional division of the rounded purchase total. Compute each posted refund in allocation sequence order against the running sum; a full refund equals the recorded RSD. The purchase date need not precede the refund date. The existing reporting view includes signed refund credits at their actual dates; do not move the purchase or allocate credits to reserves.

## D1 batch protocol for implementers

Normal preflight reads use Prisma, scoped to the household, including the purchase, its `postingDetails`, and all refund transactions with details, posting details and versions ordered by allocation sequence. Include voided rows when selecting `max(sequence)+1`; reject safe-integer overflow. Capture the complete before snapshot (purchase version and fields; refund IDs, statuses, versions, amounts and sequences) and calculate the intended after snapshot and allocations with BigInt. Reallocate later posted refunds after editing or voiding an earlier one; bump their versions and write before/after audit entries whenever their allocations change. On post, existing allocations remain unchanged. Validate the request shape and amount before building bound statements. Link is immutable on edit. The user-visible version is the refund's version; bump the purchase version for every change to the refund set or amount, and audit the purchase version change. Purchase edits already bump that version, serializing both paths.

One D1 batch must perform **all** of the following, with assertions evaluated in the batch, not solely in preflight:

1. Assert current active membership and household. On post, use the existing `posting_requests` and `idempotency_keys` namespace and request payload comparison. Replay the stored response without altering money, even if the purchase has since changed; conflicting key/payload is 409. Gate all later statements on a new claim, as for transfers.
2. Assert the purchase is the same posted expense, version below the safe maximum and equal to the preflight version, with matching category, amount, currency, original rate/source and RSD snapshot. Assert the complete refund set and each status/version/amount/sequence match the preflight snapshot, including absence of extra rows. A bound JSON array and `json_each` plus counts and null-safe `IS` comparisons can check this in a write-only assertion view; never interpolate user data. CAS the purchase version using `WHERE household_id=? AND id=? AND version=? AND status='posted' AND type='expense'`, then immediately assert `changes()=1` with `posting_write_checks`. Every other writer changing the set or refund amounts must do the same CAS.
3. Assert the new refund is linked to this expense and total posted refunds after the operation do not exceed the purchase amount; verify positive safe integer amounts and safe version/sequence bounds. Assert the destination account is active and has the inherited currency. Preserve all existing import, receipt and reserve link protections on the refund being changed. On edit/void assert its current posted status and exact expected version. Assert each affected account's projected total after removing the old refund movement and adding the replacement (if any), minus reserves, is nonnegative and total does not exceed the safe bound. Check old and new accounts, including an archived old account as existing financial writes require; an archived purchase account is unrelated. SQL integer SUM overflow must abort.
4. Write the refund transaction, immutable details (post only), posting details, positive signed account movement dated at the credit date, purchase CAS, audits, idempotency key and stored response. Each single-row update/delete must be immediately followed by `posting_write_checks(changed) VALUES(changes())`; for bulk updates, use a dedicated assertion that compares `changes()` with the exact expected count. A suppressed statement must abort before commit. A bound JSON array of after allocations may drive set-based updates; retain exact integer decimal strings and do no SQL rate arithmetic.
5. Before commit assert the complete expected after snapshot, including purchase version, all refund versions/statuses/details/allocations and movement fields/counts, affected audit before/after snapshots, idempotency response and key, and the ceiling. This catches ignored inserts and partial writes as well as stale or malformed snapshots. Use a write-only view with an INSTEAD OF INSERT trigger and `RAISE(ABORT,...)`, matching `posting_result_checks`; inspect both missing and extra rows. All writes and assertions must occur in the same batch. Map version, linked-record, eligibility, insufficient funds and snapshot conflicts to suitable 409s; failures roll back claim, movements, audits and all version changes together.

`posting_checks` now permits refund children while retaining non-refund child, parent, reserve and import guards. It blocks purchase void while posted refunds exist, purchase amount below their total, or type/category/currency changes. A trigger also protects purchase rate/source while posted refunds exist. Metadata, date, same-currency account and amount edits remain possible within these limits; after all refunds are voided the historic children do not block a normal purchase void. These guards are not a substitute for the refund-specific batch assertions above. The purchase editor must preserve the rate/source and recheck its own conversion result; account/category eligibility remains governed by the existing posting rules.

## Recovery

Apply using the normal D1 migration workflow in `migrations.md`, including a foreign-key check and recoverable backup/bookmark before a remote migration. The schema is additive and can remain unused if application code is reverted. Once refunds exist, do not drop the new table or restore an old database without reconciling subsequent financial writes; prefer a reviewed forward migration. No remote migration or recovery was performed here.

## Assertion view bindings

Bind `refund_checks(household_id,transaction_id,purchase_id,version,operation,before_json,expected_json)` after membership and key gates, before mutations. `version` is the current refund version on edit/void and null on post; operations are `post`, `edit`, `void`. `before_json` has `purchase: {version,categoryId,amountMinor,currency,exchangeRate,exchangeRateSource,rsdEquivalentMinor}` and `refunds: [{id,status,version,sequence,amountMinor,rsdEquivalentMinor}]`, including every historical refund. Amounts and sequences are decimal strings; versions are JSON integers and nullable RSD is JSON null. `expected_json` has `{accountId,amountMinor}` for post/edit and `{accountId:null,amountMinor:null}` for void. The view checks the complete set, purchase state, version, ceiling, account eligibility, linked rows and projected balances. Membership and key checks remain separate existing assertions; application BigInt validation must verify the purchase conversion snapshot and allocation math before the batch. Insert the purchase CAS after this check and assert `changes()` immediately.

Bind `refund_result_checks(household_id,transaction_id,purchase_id,operation,before_json,after_json,claim_id)` after all writes. `after_json.purchase` has the same fields as before with the incremented version; `after_json.refunds` is the complete list with the same fields plus `transactionDate`, `accountId`, `merchant`, and `note`. `after_json.audits` is `[{id,transactionId,version,beforeRequired,actorMemberId,action,detailsJson}]`: include the purchase, changed refund and every reallocated refund; `beforeRequired` is 1 for modifications and 0 only for a new refund. `detailsJson` is the exact canonical serialized audit JSON string written to the row; `actorMemberId` and `action` must also match. Audit JSON must have an `after.version` and, when required, an object `before`. The view checks every refund and movement, the ceiling, purchase and listed audits, and requires an audit and version increment for each changed RSD allocation. Post checks the persisted claim response and key. The implementation must construct the expected full before/after snapshots and audit contents from validated data rather than client-supplied assertions; the view compares each listed audit’s complete serialized details, actor and action. `refund_count_checks(changed,expected)` immediately follows each bulk statement with `VALUES(changes(),?)`; use `posting_write_checks` for one row.

The Cloudflare D1 [`batch()` documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/) specifies sequential statements in a SQL transaction and rollback of the entire sequence on failure. These assertions deliberately raise a SQL error inside the batch; checking a returned row count only after the batch has committed would be too late.
